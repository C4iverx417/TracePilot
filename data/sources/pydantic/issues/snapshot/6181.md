### Description

Hi all - first of all I'm very excited for the release of Pydantic V2! The features removed in general I think look like very good decisions. There was only one feature on the list that I felt I would miss - `allow_mutation`, in Config. I've used this in some projects before to allow users to modify large already generated models, then reinsert the modified version, rather than have to regenerate the model anew, which may have many attributes. I'd be interested to hear the reasons for its removal, or if there are any alternatives for this use case, that wouldn't involve reassigning all attributes of the model.

Here's a demonstration of the use case in V1 syntax:
```py
from pydantic import BaseModel
class NewBase(BaseModel):
    class Config:
         allow_mutation = True

class Submodel1(NewBase):
    attr1: str = 'test' # Imagine many more attributes here

class Submodel2(NewBase):
    attr2: str = 'test' # Imagine many more attributes here

class Wrapper(NewBase):
    sub1: Submodel1
    sub2: Submodel2

inst = Wrapper(sub1=Submodel1(), sub2=Submodel2())
f(inst) # Some Function
inst.sub1.attr1 = 'new'
f(inst) # Some Function
```

It's actually not renamed. it's a new config. because `allow_mutation=True` is not equal to `frozen=True`.

`allow_mutation=True` = `frozen=False`
`allow_mutation=False` = `frozen=True`

I am not totally against moving it to rename section but probably it would be better to mention using of `frozen` config in the same line.
