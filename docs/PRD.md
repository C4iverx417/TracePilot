## 1. 文档目的与决策状态

本文规定项目解决的问题、目标用户、首版范围、关键业务规则、质量指标与交付条件，供后续技术设计、开发排期、测试和作品展示使用。本文不是系统已具备这些能力的声明，也不代表模型或服务已经选定。

标记约定：

- **既定方向**：来自当前讨论，例如采用 Python，围绕开源项目技术支持，使用 RAG、LangChain 和 LangGraph。
- **建议基线**：本文为使需求具体可执行而提出的默认选择；用户可在进入实现前调整。
- **待确认**：确实需要选择，但不阻止本文形成完整草案；详见第 19 节。
- **验收目标**：未来需要实测达到的门槛，不是现有成绩。

本文交付范围为需求文档，不包含业务代码、依赖安装、外部服务开通或部署。后续实施应以评审后的范围为准。

**已确认的开发方式（用户要求，优先执行）：以“用户能完成一件事”为开发单位。每次只开发一个单位，完成并验证后必须停止，交给用户自己研究、运行和解释；只有用户明确要求进入下一单位，才能继续开发。不得将本 PRD 的完整范围视为一次性实现授权。**

第 5–15 节描述最终产品要求；第 16 节规定逐步抵达这些要求的顺序、当前边界和每步停止点。早期学习版本允许只实现当前单位的子集，不以尚未到期的最终 P0 要求判为当前单位失败；也不得因此宣称整个 P0 已完成。

## 2. 项目概述

### 2.1 一句话定义

为使用某个开源库或框架的开发者提供一个版本敏感、证据可追溯、能够追问和有限补检索的技术支持助手。

### 2.2 问题与机会

开发者排查问题时，经常需要在官方文档、迁移指南、Release Notes 和历史 Issues 之间反复切换。困难包括：

1. 搜索结果与当前依赖版本不一致，正确的新版说明可能无法解决旧版问题。
2. 报错文本、API 名称和自然语言描述混在一起，仅靠语义相似度容易遗漏精确匹配。
3. Issue 中同时存在提问、猜测、临时绕过和维护者结论，检索到文本不等于取得可靠结论。
4. 问题缺少版本或环境信息，模型容易过早给出确定答案。
5. 常见问答演示缺乏评估集、引用核验和成本记录，难以判断优化是否有效。

本项目以“帮助开发者缩小排查范围”为目标，不承诺替代维护者诊断，也不把检索相关性当成根因已被证明。

### 2.3 预期价值

- 用户价值：减少查找资料和辨别版本的时间，获得可核对的排查路径。
- 学习价值：完成数据导入、混合检索、条件工作流、后端 API、评估与部署的闭环。
- 展示价值：用真实问题、失败案例和对照实验说明工程取舍；不以框架数量作为成果。

## 3. 用户与使用场景

### 3.1 目标用户

| 用户 | 主要需求 | 首版支持 |
|---|---|---|
| 首次使用目标项目的开发者 | 理解配置、API 和基础报错 | 支持 |
| 进行版本升级的开发者 | 查找不兼容变化和迁移步骤 | 支持 |
| 遇到已有问题的开发者 | 查找历史 Issue、已知限制或绕过方法 | 支持 |
| 维护知识库的项目开发者 | 导入、更新和核查资料 | 通过管理命令支持 |
| 跨团队企业管理员 | 多租户权限、审计和知识隔离 | 首版不支持 |

### 3.2 核心场景

**S01：配置或 API 问答。** 用户提交问题及版本，系统检索对应资料，输出说明和来源。

**S02：升级后出现报错。** 用户提供升级前后版本及报错，系统结合迁移指南、Release Notes 和相关 Issue，列出可能变化、排查步骤和适用条件。

**S03：缺少诊断条件。** 用户只说“启动失败”，系统询问最关键的版本、错误原文或运行环境；已有信息保留在当前会话。

**S04：资料不足。** 系统在检索预算内找不到足够证据，返回证据缺口及下一步需要的信息，而不是补造不存在的配置或命令。

**S05：多轮缩小问题。** 用户补充“我用的是旧版”，系统更新版本约束，重新检索，旧版约束不能与此前新版结论混用。

**S06：检查答案来源。** 用户展开引用，看到资料标题、适用版本、原文片段和原始链接。

### 3.3 示例输出的含义

示例问题：“从版本 A 升级到版本 B 后，参数 X 报错，应如何排查？”其中 A、B、X 是占位符，不指代已验证的真实兼容性事实。正式演示必须采用选定项目中的真实问题与资料。

## 4. 目标、非目标与成功标准

### 4.1 产品目标

- G01：对知识库覆盖的问题给出有依据、版本适用的回答。
- G02：在信息缺失、资料冲突和无法回答时采取可理解的行动。
- G03：提供能由用户核对的引用，而不仅是一组相关链接。
- G04：证明检索与工作流优化对质量、延迟和成本的实际影响。
- G05：提供可复现的本地运行、演示和评估流程。
- G06：每个开发单位完成后，学习者能够独立运行、解释关键数据流、定位一类错误并完成一个小修改；学习与代码交付分别记录。

### 4.2 非目标

首版不提供自动执行终端命令、自动修复代码、提交 PR、任意网站爬取、私有仓库接入、全仓库代码理解、多 Agent 协作、通用互联网问答、语音或图像输入、企业多租户平台和移动端应用。

代码示例仅作为文本建议展示，不自动运行。对于可能删除数据或改变环境的步骤，应解释影响并给出必要前置检查。

### 4.3 发布条件

核心功能验收通过、固定测试集达到第 13 节目标、无未关闭的严重缺陷、可从干净环境复现演示，才可称为首版完成。不能以“界面能聊天”或“某次回答正确”代替验收。

## 5. 范围与优先级

优先级含义：P0 为首版发布必需；P1 为核心完成后的工程增强；P2 为后续方向，不纳入首版承诺。

| 范围 | 优先级 | 交付边界 |
|---|---|---|
| 单项目、两个明确发布版本的知识库 | P0 | 不是全 GitHub 搜索引擎 |
| 官方文档、Release Notes、人工筛选的 Issues | P0 | 数据来源固定且可追溯 |
| 文本问答、版本选择、关键条件追问 | P0 | 简单 Web 界面 |
| 精确词项与向量的混合检索 | P0 | 具备可切换的向量基线 |
| 条件检索、证据判断、有界重试 | P0 | 一个可观察的 LangGraph 工作流 |
| 引用、无法回答、冲突展示 | P0 | 不承诺自动解决所有故障 |
| 会话持久化、刷新后恢复、任务状态查询 | P0 | 单实例部署，支持服务重启后的查询恢复 |
| 评估集、对照实验、调用追踪 | P0 | 结果允许复现 |
| 重排器、增量自动同步、答案反馈 | P1 | 由测量结果决定是否加入 |
| 运行中的图跨进程断点续跑、实时流式输出 | P1 | 另行验证持久执行与幂等设计 |
| 多项目、权限隔离、代码级检索 | P2 | 需要独立需求设计 |

## 6. 数据范围与知识库规则

### 6.1 目标项目选择标准

建议选择一个 Python 生态开源库，且满足：维护文档清晰；有两个可定位的发布版本；有迁移或发布记录；有足够已解决问题；资料可合法用于本项目。最终项目和版本待确认。

首次数据可行性检查必须回答：是否能获取两个版本的文档快照；是否能把资料关联到明确版本；是否有足够证据标注测试问题。如果不满足，应更换项目，而不是降低版本可靠性规则。

### 6.2 建议数据规模

| 数据类型 | 初始规划量 | 导入要求 |
|---|---|---|
| 文档 | 每个版本约 30–80 个相关页面 | 包括入门、配置、相关 API 与迁移内容 |
| Release Notes / 迁移指南 | 覆盖选定版本及必要升级区间 | 保留版本标题和发布日期 |
| Issues | 30–50 个人工筛选条目 | 优先有明确解决证据、版本与复现条件的条目 |

以上是控制成本的规划范围，不是必须凑齐的数量指标。排除重复导航、无关页面、只有“同样问题”回复和无法建立适用条件的内容。

### 6.3 来源元数据

每个文档至少保存：`document_id`、`project_id`、`source_type`、`title`、`canonical_url`、`snapshot_id`、`content_hash`、`fetched_at`、`version_scope`、`version_evidence`、`status`。有条件时保存 `published_at`、`updated_at`、仓库 tag 或 commit SHA。

每个分块至少保存：`chunk_id`、`document_id`、`heading_path`、`content`、`locator`、`content_hash`、适用版本字段及解析器版本。`locator` 可采用标题锚点或本地快照中的字符偏移，不能伪造网页行号。

### 6.4 版本规则

1. UI 提供明确版本选择及“尚不清楚”选项；后者在输入中表示为 unknown，不视为系统支持的具体版本。不把“latest”作为可重现的版本标识。
2. `version_scope` 区分精确版本、经人工核对的版本范围、通用内容和未知版本。
3. 导入当前文档后，不能仅依据抓取日期将其标成旧版资料；历史资料需要 tag、归档或其他可追溯证据。
4. 普通版本问题先执行版本元数据过滤，再排序；不能仅靠提示词要求模型忽略不适用资料。
5. 通用内容只有经过人工标记后才可跨版本使用；未知版本内容不得支持版本敏感结论。
6. 比较升级前后行为时，分别检索两个版本，将证据分组后比较，不能合成一个无版本上下文。
7. 用户说“最新版”而系统无法确定其安装版本时，应展示知识库覆盖版本并请求明确版本。
8. 检索缓存如在 P1 引入，键必须包括项目、版本约束、知识库快照和检索配置，防止跨版本复用。

### 6.5 来源可信度与冲突

- 官方版本文档、迁移指南和 Release Notes 是 API 行为与变更的主要依据。
- Issue 可支持实际问题与绕过方案，但“已关闭”不能单独证明“问题已解决”。
- P0 在导入 Issue 时人工标记角色、解决证据和适用版本；未经验证的普通用户回复不能写成官方事实。
- 维护者身份依据可追溯的仓库角色或人工记录，不能由模型从语气猜测。
- Issue 指出文档缺陷时，系统应说明冲突及双方出处，不能机械地让任一来源覆盖另一来源。
- 日期较新不自动等于适用；版本匹配和结论证据优先于时间排序。

### 6.6 数据更新与撤销

P0 通过 CLI 执行导入、校验和整批重建；同一内容重复导入不得生成重复有效分块。索引以知识库快照为单位发布：导入失败不替换正在服务的完整快照。

撤销文档后，下一次发布的快照中不得再检索到其分块；旧回答保留生成时的快照引用，前端标注该来源已撤销或已过期。在线界面始终显示当前知识库快照时间与覆盖版本。

## 7. 功能需求与验收标准

### FR-01 知识库导入与发布（P0）

**要求：** 管理者使用配置文件指定允许来源、项目与版本，执行导入并查看成功、跳过、失败数量及原因。失败重试有上限；单条失败必须可定位。知识库发布前检查 URL、版本与分块关联完整性。

**验收：** 重复导入相同快照不增加重复有效记录；缺失版本证据的资料不会被发布为精确版本资料；失败批次不影响旧快照问答；重建后抽检分块能回溯到原文。

### FR-02 创建会话与提交问题（P0）

**要求：** 用户选择支持版本或“尚不清楚”后输入问题。版本未知时允许提交，由 FR-03 判断是否需要追问；不得默认补成某个版本。输入支持错误文本和代码块；保存问题、版本、时间与会话 ID。建议问题长度 1–8,000 字符、独立日志字段最多 20,000 字符；超限时明确提示。

**验收：** 空问题和格式非法的版本输入被拒绝；格式合法但知识库未覆盖的版本产生 `unsupported_version`，unknown 进入条件判断。中文问题可检索英文资料；回答语言默认跟随用户，API 名称、错误信息和引用原文保留原貌。

### FR-03 关键条件追问（P0）

**要求：** 提取目标版本、升级前后版本、错误原文、环境和相关配置。只询问会影响本次诊断的字段，不要求每次填写所有环境信息。用户选择的版本或明确陈述优先于模型推测。

**验收：** “程序无法启动”进入追问；已给出的版本不重复询问；每次最多提出三个紧密相关字段。最多两轮澄清后仍缺关键条件，返回 `insufficient_context`，列出缺口并结束本次任务。用户之后可补充信息发起新任务。澄清次数属于同一个诊断问题（episode），不是单个 run：跨任务累计，达到两轮后不再主动追问。用户继续补充时可以尝试回答或说明信息不足；仅点击“开始新问题”或新建会话才重置计数，不由模型自行判定重置。

### FR-04 版本敏感的混合检索（P0）

**要求：** 保留错误码、函数名、路径等原始词项；分别执行关键词检索与向量检索后融合。查询改写可生成英文检索表达，但不能改变用户确认的版本与错误原文。初始候选量建议两路各 20，融合去重后最多选 8 个分块进入上下文；数值可在开发集调整。

**验收：** 精确错误文本与语义近义问题均有测试；普通版本问题不混入不适用版本；跨版本比较能够检索并分开呈现两组资料。检索为空时仍能正常返回结果状态。

### FR-05 证据判断与补检索（P0）

**要求：** 检索后检查来源是否适用、是否覆盖关键问题、是否存在冲突。模型判断结果须通过结构化 schema 校验。证据不足时可以改写查询补检索，总检索轮数最多三轮，即首次一次、补检索最多两次。

**验收：** 相关性高但版本不符的资料不能通过；模型格式错误有一次修复机会，仍失败则受控返回错误；达到检索上限后进入证据不足或部分回答状态，不无限循环。

### FR-06 诊断回答（P0）

**要求：** 回答按需要包含：简明结论、适用环境、已确认事实、可能原因、按优先顺序排列的排查步骤、引用和证据缺口。必须区分“文档规定”“历史案例”“待验证假设”。对只有相关性的证据，使用“可能”“建议验证”等准确措辞。

**验收：** 仅有相似 Issue 时不能断言相同根因；每个关键事实性结论都有关联引用；排查建议说明预期观察结果及后续分支。仅能回答一部分时，将已支持部分与未支持部分明确分开。

### FR-07 引用展示与核验（P0）

**要求：** 引用包括引用 ID、标题、来源类别、版本适用范围、原文片段、原始 URL 和快照定位。模型只能从本次获准证据的 ID 中选择引用，标题和 URL 由服务端补全。

**验收：** 不存在的引用 ID 不得展示为有效引用；点击引用能看到生成时的片段与来源；引用到一页相关文档但片段不支持对应结论，仍视为引用错误。文本引用与结论支持关系需要单独评估。

### FR-08 无答案、冲突与不支持范围（P0）

**要求：** 区分知识库无覆盖、版本不支持、信息不足、资料冲突和系统故障。证据不足时说明缺少什么，并建议用户提供最小补充材料。不得把模型通用知识包装成已经检索到的项目事实。

**验收：** 知识库外问题进入 `insufficient_evidence`；未支持版本进入 `unsupported_version`；服务调用失败进入错误状态而不是声称无资料；冲突无法消解时输出 `conflicting_evidence`，显示分歧出处和验证建议。

### FR-09 多轮会话（P0）

**要求：** 保留用户确认的版本、环境及当前故障摘要。新一轮版本改变时重新检索。模型使用精简会话摘要与当前必要消息，避免无限拼接全部历史。用户可新建会话，或在现有会话中点击“开始新问题”创建新的诊断问题；新的诊断问题清除故障摘要与澄清计数，保留项目和用户显式保留的版本选择。

**验收：** 刷新页面或服务重启后可恢复已保存消息和澄清状态；两个会话不串消息或版本；用户纠正版本后旧引用不会作为当前版本结论继续使用。长会话不得超过模型上下文预算。

### FR-10 执行状态与停止（P0）

**要求：** 展示“检查条件、检索资料、核验证据、生成回答”等状态；状态是实际后端进度，不展示内部推理文本。任务可查询状态，前端断线后可重新连接查询。

**验收：** 执行有总超时、调用预算与检索轮数上限；用户可停止任务。停止是尽力取消，已发出的外部调用可能仍计费；结果不会在取消后覆盖会话。服务重启时未完成任务标为 `interrupted`，用户可重新提交，P0 不承诺从运行中节点续跑。

### FR-11 追踪与评估（P0）

**要求：** 按 `run_id` 记录输入摘要、版本约束、快照、检索配置、候选 ID 与分数、节点耗时、调用次数、token、已知价格下的估算成本和结束原因。支持导出评估结果。

**验收：** 从一条回答定位到本次检索片段和流程分支；未知价格标记为空或未知，不能计为零；日志不记录 API key。使用 LangSmith 时仅上传经过检查的演示数据，支持关闭外部追踪并保留本地结构化日志。

## 8. 页面与交互需求

首版建议使用 Streamlit，优先保证信息完整和结果可解释，不投入复杂视觉定制。

### 8.1 会话页

- 顶部：项目名称、覆盖版本、当前选择版本、知识库更新时间。
- 主区域：问题输入、可选错误日志、历史消息、任务阶段与最终回答。
- 回答下方：引用列表、检索轮数、耗时和“证据不足”等状态标识。
- 侧栏：新建会话、历史会话、演示样例；不提供任意 URL 抓取入口。

### 8.2 引用详情

展示标题、来源类型、版本、原文、快照标识、来源链接。英文原文可以附中文解释，但中文解释不能冒充原始引文。原始页面失效时仍显示本次快照片段，并说明外部链接失效。

### 8.3 失败与等待

等待阶段明确显示任务仍在处理；超时、取消、服务错误、知识库无答案采用不同提示。浏览器刷新后重新查询已有任务，不自动重复提交造成额外模型调用。

### 8.4 可访问性与内容呈现

错误信息不只通过颜色区分；支持键盘提交、代码块复制、长文本换行与滚动。模型输出和来源文本按不可信内容渲染，不执行 HTML 或脚本。

## 9. LangGraph 工作流与状态约束

### 9.1 推荐流程

```text
接收问题 → 读取会话与版本 → 校验输入
                          ↓
                    条件是否足够？
                  ┌───────┴────────┐
                  否                是
            保存澄清请求       构建受约束查询
                  ↓                 ↓
             等待用户补充      版本过滤与混合检索
                                    ↓
                              判断证据充分性
                         ┌──────────┼──────────┐
                        充分       不足         冲突
                         ↓          ↓            ↓
                     生成回答   预算内补检索  展示冲突/部分回答
                         ↓          ↓
                     引用校验   耗尽预算后说明缺口
                         ↓
                  保存消息与执行结果
```

澄清可采用应用层保存状态后结束任务、用户回复时发起下一次任务的方式。P0 不强制使用 `interrupt()`；如果采用 LangGraph interrupt/checkpointer，必须额外验证恢复行为与节点重入，不能假设外部调用具有 exactly-once 语义。

### 9.2 核心图状态

建议至少包含：`session_id`、`episode_id`、`run_id`、`question`、`confirmed_context`、`target_versions`、`kb_snapshot_id`、`query_variants`、`retrieved_evidence`、`evidence_assessment`、`retrieval_rounds`、`clarification_rounds`、`model_call_count`、`token_usage`、`deadline`、`answer`、`citations`、`outcome`、`error`。

服务端校验版本和引用等硬约束；模型负责查询理解、证据辅助判断及语言组织。不得让模型自行取消预算限制。

### 9.3 预算与退出条件

建议基线：单任务最多三轮检索、八次模型调用、一次格式修复、两次单次外部请求的瞬时错误重试，以及 60 秒总期限。请求重试消耗同一总期限并计入成本；每次实际发出的模型请求均计入调用总数，格式修复也计入，不设置额外隐含额度。

遇到 429、超时和短暂服务错误可退避重试；鉴权失败、无效模型和输入错误应立即终止。触发任一硬预算时停止新调用，保存已得证据，并返回准确结束原因。

## 10. 逻辑架构与技术边界

### 10.1 建议组件

| 层 | 建议选择 | 职责与约束 |
|---|---|---|
| 界面 | Streamlit | 会话、版本、回答、引用与状态 |
| API | FastAPI + Pydantic | 输入校验、任务创建、会话和结果查询 |
| 编排 | LangGraph | 状态、条件分支、补检索和退出 |
| 模型与检索连接 | LangChain | 模型适配、文档接口、检索与结构化输出 |
| 存储 | PostgreSQL + pgvector | 文档、分块、向量、会话、运行记录 |
| 词项检索 | Python BM25，按快照加载索引 | 首版避免另行引入搜索集群；需与数据库快照一致 |
| 评估 | Python 脚本 + 可选 LangSmith | 固定数据集、实验配置、结果导出 |
| 本地部署 | Docker Compose | 单应用实例、数据库与明确环境配置 |

以上为技术建议，不是唯一实现。数据库向量维度取决于选定 embedding 模型；embedding 或分块配置改变必须生成新索引快照。首版不要求 Redis、Celery、Kubernetes 或微服务。

### 10.2 数据流

离线：允许来源 → 抓取/读取快照 → 清洗 → 版本与可信度标记 → 分块 → embedding 与 BM25 → 校验 → 发布快照。

在线：问题与版本 → 会话上下文 → LangGraph → 检索 → 证据判断 → 回答与引用校验 → 保存结果 → UI。

开发者必须能替换模型提供商而不改变核心业务数据结构，但首版仅需验证一个生成模型与一个 embedding 模型。框架版本在实现时固定，不使用未锁定的依赖作为可复现交付。

## 11. 数据实体与接口契约

### 11.1 核心实体

| 实体 | 关键内容 |
|---|---|
| Project | 项目、支持版本、允许来源 |
| KnowledgeSnapshot | 发布状态、来源清单、配置与内容哈希、时间 |
| Document / Chunk | 原文、定位、版本证据、可信度标记、embedding 版本 |
| Session / Episode / Message | 会话、诊断问题、用户确认信息、消息、跨 run 的澄清轮数、创建时间 |
| Run | 任务状态、业务 outcome、预算、耗时、快照与配置 |
| Citation | 回答内结论与 chunk 的关联、快照片段 |
| EvaluationCase / Result | 问题、版本、标准证据、期望行为、实验输出与分数 |

每个 Run 固定一个知识库快照。执行中发布新快照不改变已有 Run 的检索范围。会话标识与图线程标识不能被视为身份认证。

### 11.2 建议 API

| 方法与路径 | 行为 | 主要返回 |
|---|---|---|
| `GET /api/v1/projects/current` | 查询覆盖范围 | 版本列表、快照、更新时间 |
| `POST /api/v1/sessions` | 创建会话 | session_id |
| `GET /api/v1/sessions/{id}` | 恢复会话 | 消息、当前 episode 与确认信息 |
| `POST /api/v1/sessions/{id}/episodes` | 开始新问题 | episode_id、重置后的诊断状态 |
| `POST /api/v1/sessions/{id}/runs` | 提交问题或补充条件 | 202、run_id、status_url |
| `GET /api/v1/runs/{id}` | 查询状态或结果 | status、outcome、answer、citations |
| `POST /api/v1/runs/{id}/cancel` | 请求停止 | 当前状态及取消结果 |
| `GET /api/v1/runs/{id}/citations/{citation_id}` | 查询引用详情 | 快照原文与来源元数据 |
| `GET /health` | 存活检查 | 服务状态，不返回密钥或连接串 |

导入使用本地管理命令，首版不开放外部导入 API。创建任务支持 `Idempotency-Key`：提交问题须关联当前 episode_id。相同会话同 key 同请求返回同一 run；相同 key 不同请求返回 409；建议保存 24 小时。每会话同一时间仅允许一个执行中任务，新请求返回 409 并告知现有 run。

### 11.3 状态与结果

任务执行状态：`queued`、`running`、`awaiting_input`、`completed`、`failed`、`cancelled`、`interrupted`。`awaiting_input` 对当前任务为稳定等待状态，后续输入创建新任务；它不是持续占用工作线程的后台任务。

业务结果 `outcome` 独立于执行状态：`answered`、`partially_answered`、`insufficient_context`、`insufficient_evidence`、`conflicting_evidence`、`unsupported_version`。例如知识库无答案可以是 `completed + insufficient_evidence`，外部服务鉴权失败则是 `failed`。

建议错误码：`INVALID_INPUT`、`RUN_IN_PROGRESS`、`MODEL_UNAVAILABLE`、`MODEL_AUTH_FAILED`、`RETRIEVAL_FAILED`、`BUDGET_EXCEEDED`、`DEADLINE_EXCEEDED`、`INVALID_MODEL_OUTPUT`。返回安全错误描述与 run_id，不暴露内部密钥、完整堆栈或连接配置。

## 12. 非功能需求

### NFR-01 正确性与可解释性

版本约束、引用 ID 和预算由确定性逻辑校验。证据是否语义支持结论结合人工抽检与评估，不把第二次模型判断当成事实保证。关键结论不展示未经校准的“95% 置信度”等数字。

### NFR-02 性能与容量

建议参考环境：记录型号与内存的开发机、单应用实例、本地数据库、远程模型 API、预建索引、最多三条并发任务。正式性能结果必须注明网络、模型、token 上限、分块量和是否使用缓存。

验收目标：至少 30 次固定回放、包含单轮与补检索问题；端到端 P50 ≤ 15 秒、P95 ≤ 40 秒；所有任务在 60 秒预算后进入可查询的终态或稳定等待态。前端轮询接口 P95 ≤ 1 秒，不能被模型请求长期阻塞。低于 30 次的结果只作为调试样本，不宣称稳定分位数。

### NFR-03 成本

记录生成和 embedding 成本，区分离线导入、在线回答和模型裁判成本。初始在线平均成本目标 ≤ 0.05 美元/任务，按最终所选模型的可核验价格计算；这是待测预算，不是费用承诺。单任务建议累计 token 上限为输入 24,000、输出 4,000；调用前估算剩余额度，调用后更新真实 usage。模型不能可靠返回 usage 时标记估算来源与误差限制。

### NFR-04 可靠性

模型失败、检索失败、异常格式和取消均有独立路径。已完成消息和澄清状态持久化。进程重启后中断任务不得永久显示 running，也不得无提示重复计费。P0 允许重新提交中断任务；运行中断点恢复属于 P1。

### NFR-05 安全与数据处理

来源、Issue 和用户输入均视为不可信数据，不能覆盖系统指令。检索内容不允许触发命令、读取本机文件或修改来源白名单。P0 导入仅由管理 CLI 使用明确允许的远程来源或本地快照，校验重定向并阻止访问内网地址；不提供用户任意 URL 抓取。

密钥从环境配置读取，不写入仓库、响应或 trace。输入和日志做基本敏感信息提示及脱敏，但不承诺自动识别所有秘密。首版默认只使用公开演示数据和合成日志。保留来源署名、链接和适用许可证信息。

### NFR-06 部署与访问边界

P0 默认本地运行或受访问控制的私人演示，不作为匿名公网服务。若要公开部署，必须先增加身份认证、用户/会话归属校验、请求限流、HTTPS 与总费用上限，并验证引用内容的访问边界；这属于扩大部署范围，不能只把本地端口公开。

### NFR-07 可维护性

数据导入、检索、工作流、API、界面和评估职责可独立修改；模型与 embedding 配置集中管理。README 说明环境、数据快照、初始化、运行、评估和已知限制。依赖锁定，日志可按 run_id 关联。

## 13. 评估设计与量化验收

### 13.1 数据集

建议先制作至少 60 条人工核对问题：20 条开发集，用于调参；40 条冻结测试集，用于最终报告。问题必须来自选定项目资料或明确构造的无答案/对抗场景。每条包含项目、版本、问题、必要上下文、期望 outcome、关键事实、可接受证据、不可接受的版本混用和标注说明。

冻结测试集建议分布：直接文档问答 10 条、跨资料综合 8 条、升级/版本冲突 8 条、需要追问 4 条、无法回答/范围外 6 条、提示注入与异常输入 4 条。分类以主要测试意图计数，允许附加标签。

澄清问题以预定义用户补充脚本继续执行，报告首轮行为与补充后的最终表现。任何可回答子集的实际样本数都必须随指标一同披露。

测试问题可由模型辅助草拟，但版本、答案和来源必须人工核对。测试集不能被拿去反复调整阈值；发现标注错误时记录修订并对全部配置统一重跑。测试问题的问答文本不能作为知识库文档导入，原始来源文档可以。

### 13.2 实验组与公平比较

| 组别 | 配置 | 目的 |
|---|---|---|
| A | 单次向量检索 + 同一生成模型 + 引用 | 基础 RAG 基线 |
| B | 版本过滤 + 混合检索 + 同一生成模型 | 测量检索与元数据策略的收益 |
| C | B + LangGraph 条件流程、补检索与证据判断 | 测量工作流的额外收益和代价 |

全部组使用相同知识库快照、生成模型、embedding 模型、测试问题、上下文预算及输出格式。A 不使用严格版本过滤时，其版本错误应如实记录。C 有额外调用预算，因此必须同时报告质量、实际调用数、token、成本和延迟，不能把所有收益笼统归因于框架。

A→B 同时改变版本过滤与检索方式，不能单独证明混合检索贡献；若简历或报告要主张混合检索提升，增加“向量检索 + 版本过滤”消融组。工作流同理，必要时单独关闭补检索或证据判断进行分析。

### 13.3 指标与门槛

以下为 C 组首版目标，并需同时展示 A、B 实测值：

| 指标 | 定义/统计范围 | 首版验收目标 |
|---|---|---|
| Evidence Hit@8 | 可回答问题中，前 8 个分块至少命中一组人工标注的充分证据的比例；多来源问题需覆盖必需证据集合 | ≥ 85% |
| 答案正确率 | 可回答问题中，关键事实与版本正确、无实质性错误且回答核心问题的比例 | ≥ 80% |
| 引用支持率 | 所有带引用的关键事实主张中，被对应片段实际支持的比例 | ≥ 90% |
| 引用覆盖率 | 回答中的关键事实主张具有有效支持引用的比例 | ≥ 90% |
| 错误版本结论数 | 版本测试中，使用不适用版本资料支持当前版本结论的次数 | 0 |
| 澄清行为 | 专门设计的澄清问题中，首轮询问关键缺口且不提前断言根因 | 4/4 |
| 无答案行为 | 六个范围外/无证据问题返回合适 outcome，未伪造答案或来源 | 6/6 |
| 引用结构完整性 | 所有返回引用均可定位到该 run 的获准 chunk 与快照 | 100% |
| 注入与异常输入 | 四个测试场景不执行来源指令，不泄露密钥，不发生无界调用 | 4/4 |
| 性能与成本 | 使用第 12 节环境和口径 | 达到预算，或明确标为未通过 |

计算百分比同时给出分子/分母，并按向上取整确定通过数。例如 26 条可回答题的 80% 目标至少需要 21 条通过。零容忍目标仅说明固定测试集内零次失败，不代表真实场景零风险。

Evidence Hit@8 对每条问题只计一次：采用任务结束时最终选中的最多 8 条去重证据。C 组可从各轮候选池合并后重新选择，但生成器实际可见的证据总数也必须最多 8 条；不得用三轮共 24 条的命中率冒充 Hit@8。另报首轮 Hit@8 和最终 Hit@8。若在回答前主动拒答，仍按最终保留的证据集合计分；空集合按未命中计。澄清用例在脚本补齐条件后的最终任务计检索分，首轮另评澄清行为。

### 13.4 评分方法

- 检索与结构性规则由脚本评分，基于允许证据 ID 集合、版本约束和引用关联。
- 答案正确性使用人工评分表：2 分为正确且充分，1 分为基本正确但缺关键内容，0 分为错误、错误版本或无依据断言。正确率仅计算 2 分案例。
- 引用以“关键事实主张—引用片段”对人工核查；开发者标出关键主张，并保留审阅记录，避免只统计容易支持的句子。
- 模型裁判可辅助定位失败，不能作为唯一的最终验收依据。记录裁判模型与提示词。
- 每种实验配置运行同一测试集至少两次，报告各次结果和波动；若预算不足只运行一次，报告明确注明单次实验。
- 产出失败分析：至少列出检索缺失、版本过滤错误、来源冲突、生成偏离、无答案误判等实际出现的类别，不为凑数编造案例。

### 13.5 改进判定

不预先承诺 C 一定优于 B。若 C 未带来质量或适当拒答的可解释改善，却显著增加延迟/费用，应在报告中说明，并可默认让简单问题走 B 路径、复杂问题走 C 路径。选择规则须在开发集上确定，再用冻结集验证，不能在看完测试答案后逐题挑选最优组。

## 16. 按用户闭环开发与学习停顿机制

### 16.1 开发单位的定义与执行规则

一个开发单位必须回答：“完成后，用户新增能完成哪一件事？”用户可以是终端使用者，也可以是导入资料的知识库管理者。每个单位同时具备输入、可观察的结果、正常验收和失败边界。CLI 是早期正式交互入口，不要求先做网页。

“把数据库建好”“搭好所有目录”“写完全部检索模块”不能独立作为开发单位；它们只能在当前用户闭环确有需要时作为内部任务。为保持易理解，单位仍过大时，可在开发前拆成更小的可演示闭环。

执行约束：

1. 每次只规划并实现当前一个单位的必要改动，未来单位仅保留文字说明。
2. 不提前生成未来代码、隐藏功能、空壳接口、大规模脚手架、依赖或基础设施；不在用户研究期间后台推进后续单位。
3. 实现当前闭环所需的最小校验、错误处理和安全要求可以一起完成，但不得据此扩展到整个最终产品。
4. 每步先用少量真实样例验证，再增加复杂性；不为低影响改动堆积与实现重复的测试。
5. 阶段代码完成与学习理解完成分别记录；代码能运行不等于用户已掌握。
6. 当前代码验证通过并交付学习材料后，**必须结束本次开发，等待用户研究与复述**。用户继续提问时，只解释或修改当前单位，不默认推进。
7. 用户明确说“开始 Uxx”“这个我理解了，继续下一步”等，才构成下一单位的执行授权。沉默、验收通过、对答案说“好的”和研究时间已过均不能自动触发继续。
8. 默认先听用户解释，再针对具体理解缺口反馈；不抢先给完整标准答案，不强制考试或凭助手主观评分阻止用户。用户明确选择跳过复述或调整节奏时，以用户最新要求为准，并如实记录。

这项逐步停止规则来自用户本次明确要求，不是额外引入的审批流程。

### 16.2 每个单位的固定协作流程

**开发前：** 说明当前用户故事、输入/输出、这次改哪些内容、引入哪些新概念、如何验证。只询问当前单位确实依赖的信息，不要求一开始决定所有模型、数据库和部署选项。

**开发中：** 围绕该故事做最少必要改动，说明关键数据流。验证正常行为及至少一个有意义的失败行为。若完成当前故事需要明显扩展范围，先解释并拆分，不能自行跨入下一单位。

**开发后：** 提交可运行结果、验证记录和第 16.5 节的学习交接卡，状态改为“等待用户研究”，立即停下。

**用户研究：** 用户自己启动、阅读代码、尝试修改或复述。助手回答问题、纠正具体误解；当前功能发现缺陷时可在该单位内修复并重新交接。

**用户要求继续：** 记录理解情况与仍待巩固点，进入紧邻的下一单位。用户可以主动要求拆分、回退、跳过或改变顺序；先同步文档中的对应边界。

### 16.3 分单位开发路线

下列路线是建议实现顺序；不是已完成清单。U01–U03 采用少量本地资料与内存索引，先理解数据流。LangChain 在 U02 引入所需的文档/embedding 接口，U03 连接检索与生成；LangGraph 到 U08 才引入。数据库、API 和网页在相应用户需求出现时加入。

#### U01：用户能在终端提问并获得模型回答

- **用户故事：** 我输入一个问题，能看到真实模型返回的文本。
- **本次边界：** 一个最小 Python 入口、一个生成模型、环境变量配置、请求超时和基本错误提示；不使用 LangChain/LangGraph，不做检索、数据库或网页。
- **验证：** 正常问题有返回；缺少密钥时能看懂原因，输出不包含密钥。记录实际调用模型与可获得的 usage。
- **用户研究重点：** 从输入到模型请求再到输出的路径；消息 role、参数、返回值、环境变量；为什么调用成功不保证答案正确。
- **动手验证：** 用户自己改一个生成参数或输出字段，并解释观察到的变化；允许变化不明显，不能强行归因。
- **停止点：** 交付运行命令和请求/响应讲解位置，停止；未经用户明确要求，不进入资料读取。

#### U02：用户能从少量资料中找出相关原文

- **用户故事：** 我输入一个技术问题，能看到最相关的文档片段及来源。
- **本次边界：** 人工选取 3–5 份可追溯资料，本地读取、分块、embedding、内存向量检索；不生成答案、不做自动爬取或数据库。目标项目在本单位确定，第二版本可到 U05 再接入。
- **验证：** 用约 5 道开发问题检查检索，其中包含直接命中、需要多个片段、无相关资料；展示分数与来源，不将相似度当成已证实的正确率。此时允许无答案问题仍返回相似候选，记录这一限制。
- **用户研究重点：** 文档如何变成 chunk、向量是什么、Top-K 的意义、分块为何会丢上下文。
- **动手验证：** 改一次 chunk size 或 Top-K，比较相同问题的检索结果。
- **停止点：** 用户能检查原文与候选后停止；不自动接上模型生成。

#### U03：用户能根据资料得到带来源的回答

- **用户故事：** 我提问后，系统依据检索内容作答，并允许我核对原文。
- **本次边界：** 将 U02 的检索结果组装进模型上下文，形成基础 RAG；服务端补全来源字段，校验引用 ID。仍是 CLI、单版本、内存索引。暂不承诺可靠拒答或自动重试。
- **验证：** 至少一个直接回答和一个跨片段回答能定位到正确来源；伪造引用 ID 被拦截。保存问题、检索片段与最终回答作为早期基线。
- **用户研究重点：** 检索输入与生成输入的区别；prompt 如何组装；LangChain 在本链路承担什么；如何判断问题出在检索还是生成。
- **动手验证：** 查看一次完整的脱敏上下文，改变 Top-K 或提示词后复查引用。
- **停止点：** 交付一次完整链路的阅读路径后停止；不自动扩展成 Agent。

#### U04：用户能知道资料不足以回答

- **用户故事：** 我问资料没有覆盖的问题时，系统明确说明证据缺口。
- **本次边界：** 增加结构化回答结果、证据不足/部分回答路径；仅一次检索，不自动补检索。加入来源指令注入的基本防护，不执行文档中的命令。
- **验证：** 固定的可回答、无答案和恶意来源样例分别符合预期；不能只靠“一律拒答”通过。当前结果仅代表这些样例，不声称普遍可靠。
- **用户研究重点：** 检索相关不等于支持结论；引用存在不等于引用正确；为什么单一相似度阈值不能保证答案。
- **动手验证：** 自己提出一个知识库外问题，检查是否错误生成确定结论。
- **停止点：** 用户能解释回答/部分回答/无法回答的区别后等待其明确继续。

#### U05：用户能获得适用于自己版本的回答

- **用户故事：** 我指定版本 A 或 B，相同问题能得到适用该版本的资料与解释。
- **本次边界：** 验证并接入两个具体版本，补齐版本证据和过滤规则；版本未知时提示选择或说明需澄清，完整多轮追问留到 U09。跨版本比较留到 U07。
- **验证：** 一组真实存在版本差异的问题分别查询 A/B；无错误混用；未知版本不会默认为最新版，未支持版本能明确返回。
- **用户研究重点：** 元数据过滤为何先于排序；历史文档如何证明版本；为什么不能只在 prompt 中写“注意版本”。
- **动手验证：** 用同一问题切换版本并比较检索候选与引用。
- **停止点：** 保存对比案例，停止；不顺带增加关键词检索。

#### U06：用户能用错误原文找到排查依据

- **用户故事：** 我粘贴错误码、函数名或报错文本，能检索到相关资料。
- **本次边界：** 在现有版本过滤上增加关键词检索与融合；保留可切换的向量检索基线，不添加重排器或搜索集群。
- **验证：** 用同一组精确词项与语义问题对比两种配置，报告命中与遗漏；不要求每题混合检索都胜出。
- **用户研究重点：** 关键词与向量的优缺点、融合去重、候选量与最终上下文数量的区别。
- **动手验证：** 针对一个失败问题查看两路候选，解释为何融合有用或无用。
- **停止点：** 交付对照记录后停止。

#### U07：用户能了解一次版本升级的变化与排查步骤

- **用户故事：** 我输入升级前后版本和报错，能看到两版本证据、迁移建议和待验证假设。
- **本次边界：** 按版本分组检索、整合迁移资料，引入少量人工筛选的已解决 Issues；标记角色、解决证据与冲突。资料仍由本地快照维护，批量发布工具留到 U12。
- **验证：** 一个真实升级问题可回溯两组证据；一个只有相似 Issue 的案例不被断言为相同根因；冲突有明确展示。
- **用户研究重点：** 为什么 closed 不等于 solved、事实与假设的区分、跨资料综合的风险。
- **动手验证：** 手工核对一个 Issue 的解决证据及版本适用条件。
- **停止点：** 用户能讲清一次排查链路后，等待继续授权。

#### U08：用户在首轮检索不足时能得到有限补检索后的结果

- **用户故事：** 首轮资料不足时，系统可以改写查询再尝试，并在预算耗尽时停止。
- **本次边界：** 首次引入 LangGraph，将既有检索和回答迁入图，加入证据判断、条件路由、最多两次补检索、调用与时间预算。保留原有基线；不做多 Agent、多轮会话或运行中断点恢复。
- **验证：** 一个首轮失败而补检索成功的案例、一个耗尽预算仍无答案的案例、一个模型格式/服务异常案例；实际调用不越限。
- **用户研究重点：** State/Node/Edge、条件边、循环终止、每次节点更新的字段；框架编排为何不等于回答更准确。
- **动手验证：** 查看一条节点轨迹，修改检索轮数上限并解释终止行为。
- **停止点：** 用户研究图和执行日志；助手不得预先实现下一阶段会话状态。

#### U09：用户能补充缺失信息后继续同一个问题

- **用户故事：** 系统询问关键条件后，我补充版本或日志，能继续本次诊断。
- **本次边界：** CLI 多轮交互、内存会话、episode 与澄清计数；版本修改触发重新检索。此时明确告知退出进程会丢失历史，持久化留到 U13。
- **验证：** 追问后补充得到回答；达到两轮澄清不无限提问；修改版本不沿用错误证据；两个会话互不串用。
- **用户研究重点：** 模型上下文与应用状态的区别；session、episode、run 的关系；哪些字段由用户确认。
- **动手验证：** 自己完成一轮追问并切换版本，说明状态变化。
- **停止点：** 交付会话状态示例后停止，不自动加数据库。

#### U10：用户能通过 API 完成一次排查

- **用户故事：** 我通过 HTTP 创建会话、提交问题和查询回答，能得到与 CLI 相同的排查结果。
- **本次边界：** FastAPI、schema、最小任务状态查询与单会话并发限制；先用内存存储，不做持久恢复、取消或完整幂等。服务仅在本地使用。
- **验证：** API 正常问答和补充条件可完成；非法输入返回明确错误；轮询不被模型调用长时间阻塞；重启会丢失任务这一限制有说明。
- **用户研究重点：** 请求/响应、202 与状态查询、校验错误、API 层与工作流的分工。
- **动手验证：** 用 API 文档或命令行调用接口，并定位一次校验失败。
- **停止点：** API 用户闭环通过后停止，不自动生成网页。

#### U11：用户能在网页完成排查并查看引用

- **用户故事：** 我打开本地网页，选择版本、输入问题、补充条件并查看来源。
- **本次边界：** 简单 Streamlit 界面连接现有 API，展示真实进度、结果与引用；不做复杂视觉、流式输出或公网部署。
- **验证：** 正常问题、澄清和无法回答均可从页面完成；引用原文可核对；普通轮询不重复提交任务。刷新后历史恢复留到 U13，重复提交幂等保障留到 U14。
- **用户研究重点：** 页面、API、图与模型之间的数据流；错误状态如何映射到页面。
- **动手验证：** 从页面的一次回答追溯到后端 run 与 chunk。
- **停止点：** 页面可演示后停止，不顺带部署公网服务。

#### U12：管理者能更新资料并发布一个可追溯知识库快照

- **用户故事：** 我通过管理命令更新或撤销资料，发布新快照，且失败批次不破坏当前知识库。
- **本次边界：** 完整导入、校验、去重、快照发布与撤销；引入 PostgreSQL/pgvector，BM25 与向量索引绑定快照。只迁移知识库，用户会话的持久恢复属于 U13。
- **验证：** 重复导入不重复；导入失败旧快照仍可问答；撤销后新检索不可见；旧回答保留其快照引用。按目标规模扩充资料，并保留实验所需的索引配置。
- **用户研究重点：** 文档、分块与快照的数据关系；发布原子性；embedding 变化为什么需要重建。
- **动手验证：** 自己更新一份资料，检查发布前后的检索和引用。
- **停止点：** 管理者闭环通过后停止，不自动增加定时同步。

#### U13：用户能在刷新或服务重启后继续已保存的诊断

- **用户故事：** 我刷新页面或重启服务后，仍能找回历史、已确认条件及等待补充的问题。
- **本次边界：** 持久化会话、episode、消息、run 和引用；已中断任务标记为 interrupted，可重新提交。P0 不承诺运行中的图从节点断点续跑。
- **验证：** 已完成消息与澄清状态可恢复；新问题重置澄清计数；重启后的进行中任务不永久显示 running，也不静默重发调用。
- **用户研究重点：** 内存与数据库、持久化边界、恢复状态与恢复执行的区别。
- **动手验证：** 在不同任务状态重启服务，解释保存与丢失的内容。
- **停止点：** 交付重启验证记录后停止。

#### U14：用户能停止等待并安全重试一次排查

- **用户故事：** 请求过慢或连接中断时，我能取消、查询或重试，避免无提示重复任务。
- **本次边界：** 取消、Idempotency-Key、期限、受控重试、完整错误码与费用记录；补齐最终运行控制。取消不保证已发出的外部调用不计费。
- **验证：** 同 key 同请求返回同 run，同 key 不同请求 409；取消后结果不覆盖会话；服务异常与无资料有不同状态；预算退出行为符合第 9 节。
- **用户研究重点：** 幂等与缓存不同、超时不等于远端没有执行、取消与计费的限制。
- **动手验证：** 重放一次请求并检查 run 数量与调用记录。
- **停止点：** 完成失败路径验证后停止，不自动开展最终全量实验。

#### U15：用户能复现实验并判断系统是否值得使用

- **用户故事：** 我能运行统一评估，看到 A/B/C 的质量、版本错误、引用、延迟与成本，演示系统边界。
- **本次边界：** 完成至少 60 条问题与冻结测试集、完整对照实验、性能与成本报告、Docker Compose 和 README；只做完成最终验收必需的集成修正，不扩展 P1/P2。
- **验证：** 第 13–15 节最终验收；运行环境与快照明确，未达标结果如实展示。与早期实验保持配置可追溯，历史基线若使用不同快照必须在同一最终快照重跑。
- **用户研究重点：** 公平对照、数据泄漏、指标分母、消融、成本与质量取舍；如何用证据说明个人贡献。
- **动手验证：** 用户独立启动、运行一组评估，并讲解一个成功案例和一个失败案例。
- **停止点：** 项目首版完成或明确标记未通过项；后续优化仍须用户提出，不自动进入 P1。

### 16.4 最终要求与开发单位的对应关系

此表中的“首次涉及”不代表当时就需实现整个 FR；“完整验收”表示最终要求应在相应单位具备。某单位依赖的通用安全约束应从首次引入相应能力时遵守。

| 最终要求 | 首次涉及 | 完整验收 |
|---|---|---|
| FR-01 资料导入与发布 | U02 | U12 |
| FR-02 提交问题 | U01/U03 | U11 |
| FR-03 条件追问 | U05 | U09 |
| FR-04 版本与混合检索 | U02 | U07 |
| FR-05 证据判断与补检索 | U04 | U08 |
| FR-06 诊断回答 | U03 | U09 |
| FR-07 引用核验与展示 | U03 | U13（含历史快照） |
| FR-08 无答案与冲突 | U04 | U09 |
| FR-09 多轮与恢复 | U09 | U13 |
| FR-10 任务状态与停止 | U08/U10 | U14 |
| FR-11 追踪与评估 | U01/U02 | U15 |
| 性能、成本、部署与总体发布条件 | 各单位遵守当前相关约束 | U15 |

评估从 U02 的少量开发问题开始，逐步扩充；最终冻结测试集在 U15 实验前固定并与开发数据分离。早期探索问题不应无标记混入最终冻结测试集。来源快照、模型、参数和检索配置应随着每次实验一起记录。

### 16.5 每步必交的学习交接卡

开发者在每个单位结束时，给用户一份简洁交接卡；可放在该次交付消息或当前单位记录中，不要求额外搭建文档系统：

```text
当前单位：Uxx + 用户能完成的事
实现范围：本次真正新增了什么、已知限制
运行方式：从当前环境实际验证过的命令和输入示例
阅读路径：先读哪个文件/函数，再读哪个，附关键入口
数据流：输入 → 关键处理 → 输出
验证结果：正常、失败样例及实际结果；未验证项明确说明
研究问题：围绕当前代码给出 3–5 个具体问题，先不给标准答案
动手任务：一个小修改或故障定位，不是下一阶段功能
停止状态：代码验证完成，等待用户研究；未开始下一单位
```

默认由用户先说明“它怎么工作”“这样设计的原因”“出错时先看哪里”；助手依据实际代码反馈。不能只给概念题，也不要求背诵库源码。不把运行成功、用户在线或一句“好的”推断为理解完成。

### 16.6 理解记录与推进门槛

每个单位建议记录四项：

- **运行：** 用户能自己启动，重现正常和失败样例。
- **解释：** 用户能沿真实代码说清输入、处理与输出，知道新引入概念的作用。
- **定位：** 用户能区分当前功能最主要的两类故障，例如 U03 的检索问题与生成问题。
- **修改：** 用户能完成一个小修改并解释观察结果；助手可以指导，不冒称用户独立完成。

状态使用：`未开始 → 当前开发 → 代码已验证/等待用户研究 → 用户已复述/待巩固 → 用户明确授权下一步`。若验证失败则留在当前开发；若用户直接要求继续，记录“用户选择继续，理解情况未完整验证”，尊重用户决定。

初始记录：全部单位未开始。本次仅修改需求文档，不代表 U01 已获开发授权或已经实现。学习期间的修复仍归当前单位，不自动改变后续单位状态。

### 16.7 工期与资源安排

原先约 60–90 小时仅可作为完整首版的初步工程工作量参考，尚未计入用户研究、复述、动手练习、返工及模型调用等待。现在以学习理解为推进依据，不作固定 4–6 周或其他完工日期承诺。

每个单位开始前，只评估当前故事所需时间与费用；单位过大就拆小。不能为了赶日历进度压缩研究停顿、跳过理解交接或一次完成多个单位。需要改变范围时，显式更新需求与单位边界。

## 17. 风险、取舍与缓解

| 风险 | 影响 | 缓解与触发条件 |
|---|---|---|
| 历史版本文档不可获取 | 版本敏感需求无法成立 | U02 初筛、U05 验证；失败时更换项目或明确缩小版本范围 |
| Issue 解决证据模糊 | 错把猜测作为根因 | 人工筛选并保留解决依据；宁可少量高质量 |
| 文档分块破坏代码上下文 | 检索命中但内容不足 | 按标题/代码边界分块，人工抽检并记录配置 |
| 追问过多或补检索无收益 | 用户等待长、费用增加 | 固定预算，用 B/C 对比决定路由 |
| 模型自评不可靠 | 证据不足却生成确定结论 | 硬约束校验、人工冻结集、失败分析 |
| 数据集过小或标注偏差 | 实验结论被夸大 | 披露样本量、人工复核、多次回放、不宣称总体可靠性 |
| 模型或价格变化 | 成本与结果不可复现 | 保存模型标识、参数、日期与价格依据 |
| 外部页面变化或失效 | 引用无法核查 | 固定快照、内容哈希和来源定位 |
| 项目范围扩张 | 超出个人时间预算 | P0/P1/P2 边界与阶段退出条件 |
| 公网演示被滥用 | 数据与费用风险 | 默认私人演示，扩大访问前落实部署前提 |

## 18. P1/P2 后续演进条件

- **重排器（P1）**：仅在证据显示候选池包含正确资料但排序不足时引入，并单独测量收益与延迟。
- **自动同步（P1）**：先解决差量更新、来源撤销、限流与快照一致性，再增加计划任务。
- **图断点恢复（P1）**：先定义 checkpoint 存储、节点重入和外部副作用幂等，再承诺重启续跑。
- **流式输出（P1）**：必须保持最终引用校验，不把未经校验的事实直接作为稳定答案呈现。
- **多项目或代码检索（P2）**：重新设计项目隔离、符号定位、代码版本、依赖关系与评估集。

以上仅记录演进方向，不属于首版发布条件。
